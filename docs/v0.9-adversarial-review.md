# uikit-chat-list v0.9.0: adversarial review

Reviewed: tag `v0.9.0` of `skills/uikit-chat-list/SKILL.md`, `references/measuring-text.md`, `references/table-view.md`, `agents/uikit-list-reviewer.md`, and `docs/uikit-chat-list-sources.md`. The evidence read was the benchmark repo's `docs/round5-dataset-findings.md`, `round5-e7` to `e11-results.md`, `round5-v07-diagnosis.md`, `round5-v08-spikes.md` and `round5-v09-spikes.md`. API claims were checked against the iPhoneOS 26.4 SDK headers where the headers say something. Where only Apple's online reference says it, the finding says so.

Method: reading and reasoning only. No spike was run, because the machine had to stay quiet while a build was being scored. The spikes that would settle the open points are listed at the end.

The review is hostile by design. The skill does what it set out to do: two Opus builds on v0.9 pass every check. The question here is different: what does it teach a normal chat app that is wrong, and what does it get wrong about UIKit?

## Summary

- **The skill is tuned to one scorer.** Four rules make the benchmark's numbers better and are wrong, or unproven, for a typical chat app: the 0.1 s update timer (rule 8), prefetching off, TextKit 1 for every text view, and "trim with reloadData" (rule 12). Prefetching off and rule 8 contradict the skill's own earlier evidence.
- **Two UIKit claims are wrong as written.** Rule 12 says a delete and an insert in one batch is an assertion crash. That is not UIKit's behaviour; the crash came from a wrong index. The text size recipe relies on `targetContentOffset(forProposedContentOffset:)` being called after a plain invalidation, which Apple documents only for transitions and update animations.
- **Big gaps for real apps:** the keyboard and input bar, right-to-left languages, VoiceOver (actions, announcements, focus), media rows, day sections, and every trait other than text size (Bold Text, display scale, layout direction).
- **Evidence is thinner than the wording suggests.** Prefetching off rests on a 1 to 2 MB change inside pass-to-pass spread. "Self-sizing is not faster" contradicts the measurement. "Self-sizing crashes" was a debug label's fault. Every v0.8 and v0.9 number comes from one simulator, and the phone was never re-run.
- **Hygiene:** no build, round, harness or number names leak, but benchmark vocabulary does: "Reset" five times, "UI tests waiting on an element", "the given numbers", "the device size you were given", "screenshots", "Stop when the checks pass", and a whole "Shortcuts that do not count" section that only makes sense with a scorer.
- **Cost:** SKILL.md is 1,915 words. About 350 to 450 can go without losing behaviour in a real app. The reviewer agent states its nine items twice.

Severity scale: **High** = teaches wrong UIKit behaviour or hurts a normal app that follows it; **Medium** = a real gap or an evidence problem an agent will trip on; **Low** = wording, scoping, hygiene, cost.

## High

### H1. Rule 8: the 0.1 s timer adds latency everywhere, and contradicts the skill's own evidence

> "collect the messages and reactions that arrive within a tenth of a second and apply them as one batch update (much cheaper than one per message; the next run-loop turn groups almost nothing)"

**Why it is wrong or risky**
- A fixed trailing timer delays *every* change by up to 100 ms, even a single message on an idle list. That is 6 frames at 60 Hz and 12 at 120 Hz.
- It covers the user's own sent message (no exemption), the typing indicator and their own reactions. Users notice that: a sent bubble that appears late feels broken.
- At normal chat rates (well under one message a second) a timer groups nothing, so it adds latency and saves nothing.

**Evidence**
- The dataset that seeded the skill (`round5-dataset-findings.md` §1.10) lists "Redrawing the stream only every 100 ms" as a **bent rule**, a shortcut not allowed. Its conclusion: "apply every message as it arrives, or in batches no wider than one frame".
- §1.1 "Cost per update matters, not update count": on the phone, uncoalesced and coalesced builds cost the same (11.7 to 11.8 s against 12.0 to 12.2 s). The sources doc still says this ("no gain on an iPhone 12").
- v0.8 then made 100 ms the rule from one unpolled simulator spike (6.49 to 4.92 s) at a benchmark rate of 20 messages a second. The "Shortcuts" line moved its own limit to exactly 100 ms, so the rule now sits right on the line that used to define cheating.
- The finding that "the next run-loop turn groups almost nothing" is an artefact of the stream arriving on separate turns. That says nothing about the flush shape, only about where this generator fires.

**Fix**
- Replace the trailing timer with a *leading-edge, frame-bounded* flush. When nothing is pending, apply at once. While changes keep arriving, apply at most once per display frame, driven by a `CADisplayLink` or a run-loop observer before the Core Animation commit; add a cap of N frames only if measured.
- Always apply the user's own sends at once.
- Keep the second half of the rule ("each update costs only its rows"), which the v0.7 evidence supports well.
- Spike S3 (below) measures both CPU and the latency to the first frame.

### H2. Rule 12 misdescribes UIKit; the fix it prescribes is heavier than the bug

> "Inside one batch, deletes count positions in the old list and inserts in the new one; mixing a trim with an append is an assertion crash. Trim as its own step: remove the old rows, `reloadData`, set the final offset"

**Why it is wrong or risky**
- The first sentence is Apple's documented contract for `performBatchUpdates`: deletes are resolved against the old state, inserts against the new one. It is exactly why mixing them is *legal*.
- The crash only follows if inserts are indexed in old coordinates. The rule reads as "UIKit cannot do this", so a reader learns to avoid a normal operation instead of learning the index rule.
- `reloadData` throws away every visible cell (they all reconfigure), drops VoiceOver focus and any running animation, and turns a cheap trim into a full reload.

**Evidence**
- `round5-v07-diagnosis.md`: the faulty batch inserted at `oldCount...`. The agent's two-minute fix was `oldCount - trimmed`, and "the shipped build does not have it". The crash happened in a Debug build during development, not in the scored app.
- `round5-v08-spikes.md`: trims cost about 0.33 s in total per stream, and trim variants "gain nothing". No measurement favours `reloadData` trims over a correct mixed batch. The rule is folklore built on one index bug.

**Fix**
- Reword: "In one batch, deletes use positions in the old list and inserts use positions in the list after the deletes. An append after trimming `k` rows inserts at `oldCount - k`."
- Keep "trim as its own step with `reloadData`" only as the simple option for large trims, and keep "supply the final offset" (rule 2), which is the real reason trims break pins.
- The reviewer's item 3 should check index arithmetic, not forbid the mix. Spike S2 checks it.

### H3. "Prefetching off" is unconditional, under-evidenced, and disables data prefetching too

> SKILL: "`isPrefetchingEnabled = false`: cells prepared ahead of a list pinned at the bottom raise peak memory and gain nothing."
> Reviewer item 5, Wrong: "cell prefetching left on in a list pinned at the bottom"

**Why it is wrong or risky**
- Apple's reference for `isPrefetchingEnabled` (online docs; the header has no comment) says that setting it to false also disables data prefetching, so `prefetchDataSource` stops being called. A real chat app that prefetches avatars, thumbnails or link previews loses that silently.
- Cell prefetching exists to spread cell building across frames while the *user* scrolls (WWDC21 10252, which the sources cite for exactly this). Here the reader is pinned only some of the time; flinging up through history is the normal case.
- "Gain nothing" was never measured for user scrolling. The scored stream keeps the list pinned.
- The reviewer turns a soft tip into a hard fault in every app.

**Evidence**
- `round5-v09-spikes.md`: prefetching off alone moved the peak from 49.2 to 47.0 MB (-4 %), and the spike itself rates the split "medium… each alone moves the peak by 1 to 2 MB, within pass-to-pass spread".
- The shipped arm in the same sitting ranged 48.4 to 51.1 MB. This is inside noise and far inside the 10 to 15 % control drift (`round5-e9-results.md`).
- The TextKit 1 change explains the memory just as well.

**Fix**
- Drop the bullet, or scope it: "If peak memory matters more than scroll smoothness, and you use no `prefetchDataSource`, measure with prefetching off."
- The reviewer should report it as a note, never as Wrong. Spike S4 measures hitches while flinging up through history, with prefetching on and off.

### H4. The text size and rotation recipe relies on `targetContentOffset` being called where Apple doesn't promise it

> "On a text size change … capture the anchor, empty the saved heights, re-measure, invalidate, and return the anchored offset from `targetContentOffset(forProposedContentOffset:)`."

**Why it is wrong or risky**
- The SDK header (`UICollectionViewLayout.h:135`) documents this method as "the content offset to be applied during transition or update animations". A bare `invalidateLayout()` is neither.
- The skill's own evidence says the method is not consulted on `reloadData` (`round5-v08-spikes.md`, jump phases).
- Whether it runs after a plain invalidation can differ between iOS versions. Rotation is a bounds change, which is a different path again.
- An agent that trusts the recipe gets a pin that holds only when some other update happens to trigger the method. That is the "intermittent" loss the skill warns about elsewhere.

**Evidence**
- The E10 and E11 builds pass text size, but neither result says whether they relied on the callback or also set the offset directly. The sources map this line to `F1.5 S3, SC3` and `SDK-UITraitCollection`, and nothing there shows the callback firing on invalidation.

**Fix**
- Say both, in order. Invalidate, then call `layoutIfNeeded` once (outside any of the list's own callbacks, rule 11), then set the anchored offset explicitly, without animation.
- Implementing `targetContentOffset` as well is harmless and covers the update-animation path.
- Alternative: apply the change through `performBatchUpdates` (with no row changes) inside `performWithoutAnimation`, which *is* an update.
- Spike S1 checks on iOS 18 and 26.

### H5. No keyboard or input bar: the most common pin-breaker in a real chat app

**Gap.** Nothing on the keyboard, the composer or `adjustedContentInset`.

**Why it matters**
- When the keyboard appears, an interactive dismiss runs, or the composer grows from one line to five, the bottom inset changes. A pinned reader must stay pinned, and an unpinned reader must keep their row.
- The skill's pin logic is "read pinned before the update" for *data* updates only.
- `shouldInvalidateLayout(forBoundsChange:)` = width-only is correct, but inset changes don't change bounds. The offset correction has to come from the view controller.

**Fix.** A short section:
- Pin the composer to `view.keyboardLayoutGuide`.
- Set the list's bottom inset from the composer's frame in `viewDidLayoutSubviews`.
- Before an inset change, read pinned and the anchor; after it, restore the pin, or the anchor row's distance, without animation, or alongside the keyboard animation using its curve.
- `keyboardDismissMode = .interactive` must not trigger a re-pin per frame.

### H6. Dynamic Type invalidates more than heights; other traits are ignored

> measuring-text: "Build [the attributed string] once per message and keep it with the height, then hand that same string to the cell."
> SKILL: "On a text size change (register for `UITraitPreferredContentSizeCategory`) … empty the saved heights"

**Why it is wrong or risky**
- The attributed string holds concrete `UIFont`s. Emptying only the heights leaves the old-size strings, so the cell draws at the old size and the new heights are measured from either old or rebuilt strings, depending on the agent.
- If the text view has `adjustsFontForContentSizeCategory = true`, it rescales its own font *before* the measurer runs, which breaks the "same settings" pairing.
- Text size is not the only trait that changes text metrics:
  - `UITraitLegibilityWeight` (Bold Text) changes glyph widths, so line breaks and heights change.
  - `displayScale` changes the pixel grid the v0.9 snapping uses: an external display, a Mac running the iPad app, an iPad moving between screens.
  - `layoutDirection`.

**Evidence.** None either way. These cases were never exercised; the benchmark changes text size only.

**Fix**
- Key the stored string *and* height by message id, and empty both on any of: content size category, legibility weight, display scale, width.
- Register for all four.
- Say "message text views: `adjustsFontForContentSizeCategory = false`; fonts come from the stored string, rebuilt on change".

## Medium

### M1. TextKit 1 for every text view: right for read-only bubbles, wrong as a blanket rule

> "Message text is a TextKit 1 `UITextView` (`UITextView(usingTextLayoutManager: false)`) … A default TextKit 2 text view redoes viewport layout and selection rects on every cell setup"

**Why it is risky**
- The measured win (-25 % stream CPU, `round5-v09-spikes.md`, high confidence) is real *for many short, read-only, selectable views in reused cells*.
- The rule's wording doesn't limit it to that.
- An agent may switch the composer, a message detail view or any editable field to TextKit 1. There, TextKit 2 is Apple's default and direction, Writing Tools in a TextKit 1 view gets only its limited panel experience, and the newer text features target TextKit 2 first.
- Unverified for TextKit 1 cells: Genmoji (adaptive image glyphs), complex scripts and mixed-direction text measured against drawn.
- The v0.9 spike quotes the `UITextView.h` comment ("avoids inefficiencies associated with the needless creation of a NSTextLayoutManager") as support. That comment is about avoiding the *fallback* when code touches `.layoutManager`, not about TextKit 1 being cheaper in general. The measurement is the evidence; the quote is not.

**Missing**
- Reading `.layoutManager` on a TextKit 2 view silently falls it back to TextKit 1, with a console warning. That is the common accidental case, and the reviewer doesn't grep for it.

**Fix**
- Scope to "read-only message text in reused cells". Keep TextKit 2 for the composer and anything editable.
- Add "never read `.layoutManager` on a TextKit 2 view".
- Reviewer item 6: grep `.layoutManager` on views made without `usingTextLayoutManager: false`.
- Spike S5 covers Genmoji, Arabic and Hindi text, and Writing Tools on a selection.

### M2. The self-sizing claims misstate the evidence

> SKILL: "Self-sizing rows are not faster, they are wrong: a self-sizing collection layout can crash on a text size change at the bottom (core rule 11)"
> Rule 11: "a flush there crashes it"

**Why it is wrong**
- E2 measured self-sizing as *faster* on text size mid-list: frame 47 against 54.5 ms, app work 17 against 25.5 ms (sources, `E2`). `measuring-text.md` says "no slower", so the two files disagree.
- The crash was caused by the test adapter's debug label calling `layoutIfNeeded()` from `scrollViewDidScroll`. After that fix: "no crash, pinned after 4 of 6" (`E2-followup`). Self-sizing does not crash; it loses the pin.
- Rule 11's "crashes it" is true only for a flush that runs *during* the collection view's own pass, which in practice needs self-sizing content offset adjustments. With saved heights the risk is mostly cost.
- The cell provisioning and invalidation parts of rule 11 are extrapolation, though sound advice.

**Fix**
- "Self-sizing rows are about as fast but lose the pin after large removals and at text size changes; keep saved heights for the pin."
- Rule 11: "a flush there can re-enter the collection view's layout and assert".
- Remove "or crash" from rule 4.

### M3. Pixel snapping: no scale source, no invalidation, no tolerance

> "Snap each row's top and bottom to the pixel grid in the layout (round the running position, not each height)."

**The problem.** The evidence is strong: a deterministic 0.12 pt sliver trace that the fix closed in 3 of 3 passes. But the rule leaves out:
- **Where the scale comes from.** It must be `collectionView.traitCollection.displayScale`; `UIScreen.main` is deprecated and wrong on other displays.
- **That a scale change must re-snap everything** (H6).
- **That "ceil the measured height" means ceil to the pixel, not to the point.** Otherwise heights move to whole points and the spacing alone puts edges off the grid.
- **That other sources of fractional geometry remain:** content insets, a translucent header's height, supplementary views.

The rejected "under 1 pt is not the top row" tolerance is the defence against those.

**Fix**
- Name the scale source and invalidate on a scale change.
- `ceil` to the pixel.
- Keep the anchor lookup tolerant as well ("ignore a row showing less than one pixel"): belt and braces, not instead of snapping.

### M4. Right-to-left languages: a custom layout doesn't mirror unless told to

**Gap.** `UICollectionViewLayout.flipsHorizontallyInOppositeLayoutDirection` defaults to false (`UICollectionViewLayout.h:140`). A custom layout that places outgoing bubbles on the right keeps them there in Arabic and Hebrew. Nothing in the skill mentions the layout direction, `.natural` text alignment, or measuring mixed-direction text.

**Fix**
- Override `flipsHorizontallyInOppositeLayoutDirection` to return true, and lay out in leading and trailing terms.
- Paragraph styles use `.natural` alignment and writing direction.
- Add it to the reviewer.

### M5. VoiceOver is covered only as a cost claim

**Gaps**
1. Reply is reachable only through the text edit menu or a context menu. VoiceOver users need `accessibilityCustomActions` on the row.
2. New messages while pinned should be announced (`UIAccessibility.post(notification: .announcement, …)`), and the auto-pin must not yank the view while VoiceOver focus is on an older row.
3. Trimming and jumping with `reloadData` drop VoiceOver focus (see H2).
4. A selectable `UITextView` inside a cell is its own element. Decide whether the row combines sender, time and text.

**Evidence problem.** `table-view.md` claims the table costs "several times more" under "assistive technology polling the screen". The measurement was XCUITest `waitForExistence` snapshotting (30.7 s against 8.25 s). VoiceOver was never measured, and the sources mark the cause "a guess". The E1 table column also ran under a harness fault.

**Fix**
- Add the four points.
- Restrict the table cost claim to what was measured ("under constant UI automation queries") or drop it. It is a reason that applies only in the benchmark.

### M6. "One section" rules out day headers

> "One section, stable message ids, explicit row changes … never one section per message."

Sections by day with sticky date headers are standard in chat apps. The evidence is against one section *per message* (S2 and SC2), not against a few sections. The skill never mentions supplementary views in the custom layout either.

**Fix.** "Few sections (one, or one per day), never one per message. Date headers as supplementary views or header rows in the same layout."

### M7. Images and media: "never a bitmap" overreaches

> "Image placeholders are a background colour, never a bitmap."

The evidence (`round5-dataset-findings.md` §1.8) is a *full-size* decode (up to 1200 × 900) into an *uncapped* `NSCache`. Blur placeholders and downsampled thumbnails are normal and fine when decoded at display size into a capped cache. Media rows also need a height before the image loads (from width and height metadata), and a late load must not move the reader. The skill says none of this.

**Fix**
- "No full-size decodes. Thumbnails at display size in a capped cache; placeholder colour when there is no thumbnail."
- Media height comes from metadata and is stored like text height.
- An async size change goes through the same anchor and pin path as an edit.

### M8. The reviewer marks normal behaviour as Wrong; the checklist and the reviewer differ

- **Animated deletes.** Item 4 marks "animated deletes" Wrong. A user deleting their own message expects an animation. The skill's real point is that UIKit must not animate the *offset*.
- **Prefetching.** Item 5 marks prefetching left on as Wrong (H3).
- **Divergent lists.** The reviewer says its checks are "word for word as in the skill", but its expansions add checks the checklist lacks: pixel snapping (item 4), prefetching (item 5) and the ranges-only edit menu (item 1). A checklist-only agent misses them.

**Fix**
- Allow animated row deletes as long as the final offset is supplied.
- Downgrade prefetching to a note.
- Either add the extra checks to the checklist lines, or stop claiming the two lists are identical.

### M9. The jump recipe can be misread

> "set the offset from the layout's own frame for the target … before the list lays out: right after `reloadData`, then one `layoutIfNeeded`."

**The problem.** After `reloadData` the custom layout hasn't prepared, so `layoutAttributesForItem(at:)` can return the *old* window's geometry. "Before the list lays out" and "the layout's own frame" pull in opposite directions.

**Fix.** "Compute the target's top from your height store (the same numbers `prepare()` will use), set the offset, then `layoutIfNeeded` once." Also, "about 10 rows above, 30 below" reads as a measured constant. Say "a screen or two above and below".

## Low

- **L1. Benchmark rules in a general skill.**
  - Rule 9 (touch-to-frame timing), rule 10 (Release strip), "Shortcuts that do not count" and most of "How to work" (test runs, simulators, "the given numbers", "Stop when the checks pass") are about being scored, not about chat lists.
  - Rule 10 also lacks a scope: `STRIP_STYLE = all` is the app target's default and wrong for a framework or extension target that exports symbols.
  - Fix: move these lines to a benchmark-only workflow note outside the installed folder, or keep them in one short "When you are measured" section clearly marked optional.
- **L2. Misfiled properties.** `selfSizingInvalidation` and `isPrefetchingEnabled` sit under "The layout class" but are `UICollectionView` properties. An agent may try them on the layout. Move them to a "The collection view" line.
- **L3. Width changes wipe the cache.** "Empty it when the width … changes" makes Stage Manager live resize and rotate-and-back re-measure everything each time. Key heights by width, and keep the last two widths.
- **L4. One message growing (streamed answers, LLM-style replies) is not covered.** Re-measuring the whole long message per chunk is quadratic. Guidance needed: measure the last paragraph incrementally, or throttle per frame (see H1); shift only the tops below it.
- **L5. "Second page" is iPhone-specific.** On iPad and Mac the edit menu is a vertical list, so order doesn't hide items. The rule is harmless everywhere; just don't state it as universal.
- **L6. Table pin claim.** "Setting `contentOffset` after `endUpdates` … is undone at the table's next layout pass" is measured once (E1, pin lost after the third message) with no cause found. State it as observed, not as UIKit's contract.
- **L7. The sources doc is stale.**
  - The tag map still calls rule 8 "Apply as they arrive" and has no row for rule 12 (added in v0.7).
  - "What the sources do not give" says TextKit 1 against TextKit 2 was never timed, and that pixel rounding rests only on S3's notes. v0.9 measured both.
  - It still says "The skill says 'apply as they arrive'".
  - A reviewer of the skill can't trace v0.7 to v0.9 rules from the tag map. Fix: one row per current rule, with the v0.7, v0.8 and v0.9 evidence.

## Spikes to run when the machine is free

Each one is a tiny app with compile-flag arms, unpolled, three passes, same simulator, as in the round5 spikes.

1. **S1 (H4).** Is `targetContentOffset(forProposedContentOffset:)` called after a plain `invalidateLayout()` plus `layoutIfNeeded()` for a text size change, on iOS 18 and 26? Compare against an explicit offset set and against `performBatchUpdates(nil)`. Log each call.
2. **S2 (H2).** One `performBatchUpdates` that deletes `0..<k` and inserts at `oldCount - k`, on the custom layout. Expect no assertion. Compare its cost and VoiceOver focus against the `reloadData` trim.
3. **S3 (H1).** Leading-edge, per-frame flush against a 0.1 s trailing timer against per message, at 20/s and at 1/s. Measure CPU and the latency from arrival to the first frame showing the row. Include a local send.
4. **S4 (H3).** Prefetching on against off while flinging up through 2,000 rows (hitch time ratio), with and without a `prefetchDataSource` loading thumbnails, plus peak memory.
